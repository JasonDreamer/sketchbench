# Sketchbench 設計書

Nov 9, 2026 · @Jason

## 目的と要件

アイデアを文章で伝えると、AIがコードを書き、数秒でプレビューでき、そのまま映像ファイルに書き出せるローカル環境を作ります。アイデアごとにアプリ化やビルドをする必要はなく、1アイデア=1フォルダで完結します。

| 要件 | 設計上の答え |
| --- | --- |
| AIがコードを組む前提 | プロジェクトは普通のファイル群。AIはファイルを直接編集し、MCP経由でプレビュー画像やエラーを確認する |
| 人も介入できる | 内蔵エディタ(CodeMirror 6)でも、VS Codeなどの外部エディタでも同じファイルを編集できる。保存で即ホットリロード |
| タイムライン | 描画を「時刻tの関数」として書く。シーク、ループ範囲、キーフレーム、音声・MIDIトラックを持つ |
| 外部ファイル接続 | assetsフォルダに置くだけで読み込める。音声とMIDIは事前解析して時刻で引ける形にする |
| 気軽な書き出し | プラグイン不要。MP4、連番PNG、アルファ付きProResをボタンかコマンド一発で |
| 思いつきですぐ試す | テンプレートから新規作成、変更のまとまりごとに自動で履歴(git)に残して比較・巻き戻し |
| 単体アプリで軽く快適 | Windows専用のTauriアプリ。重い処理はRust側、スケッチの実行はUIと別プロセスにして画面を止めない |

## 方針の判断

**言語は自作せず、TypeScriptと既存ライブラリを使います。** AIの出力精度は学習データに多く含まれるAPIほど高く、MCPやドキュメントで渡せる情報はそれを補う程度にとどまるためです。自作するのは `defineSketch`、`t`、`assets` などの薄いランタイムAPIだけにし、AGENTS.mdと型定義に全部載せられる大きさに抑えます。描画部分はp5.js、three.js、GLSL、Canvas2Dをそのまま書くので、AIが得意な書き方がそのまま使えます。型チェックのエラーは `get_diagnostics` でAIに返し、AI自身に直させます。

**アプリはTauri(Rust + WebView2)で作る、Windows専用のデスクトップアプリにします。** macOSは対象外です。WindowsのWebView2はChromium系なので、WebCodecs、WebGL、WebGPUの挙動はChromeと揃います。Chromiumを同梱しない分、Electronより配布サイズと常駐メモリが小さくなります。

**操作の快適さは次の設計で確保します。** 体感を左右するのは、重いスケッチを動かしていてもUIが止まらないことです。

- スケッチはUIとは別のWebView2環境で作ったWebViewで実行し、プロセスを分ける。無限ループや重い処理でもUIは応答し続け、スケッチWebViewは仮想時計に置き換える前のsetIntervalで500msごとに生存通知を送り(ランタイムは差し替え前のsetTimeout・setIntervalも保持する)、2秒途切れたら(書き出し中とsetup実行中は設定値。既定30秒。非表示のページのタイマーはChromiumが間引き、フェーズ0では最小化したウィンドウでタイマーが数分止まった。スケッチ用環境には --disable-background-timer-throttling を付け、最小化中と子WebViewを隠している間は判定を止める)Rust側がそのWebViewを作り直して直前の正常なコードで再開する(フェーズ0の計測では、検知まで約1.8秒、作り直しから読み込み完了まで約0.2秒)。WebGLのコンテキスト喪失(GPUリセット)も同じ手順で復旧する。WebView2のProcessFailedイベント(レンダラー・GPU・ブラウザプロセスの終了)も監視してすぐに作り直す。作り直した後は再生を止め、失敗したコードのハッシュと時刻を記録して自動では再実行しない。GPUのリセット(TDR)が起きたときはUI側の環境も作り直す(フェーズ0のシェーダー無限ループ試験では、落ちたのはスケッチ環境のGPUプロセスだけで、UIの環境は無事だった。GPUが占有されている間はUIも数秒止まるため、アプリが組み立てるISF・shaderレンダラーのシェーダーにはループ回数の上限を自動で挿入する)
- タイムライン、波形、カーブはCanvasで描き、DOM要素を大量に作らない
- UIフレームワークは更新コストの小さいSolidを使う
- コードエディタはMonacoより軽いCodeMirror 6にし、補完と型エラーはTypeScript 7(ネイティブ版)の言語サーバーから受け取る。言語サーバーはRustコアが子プロセスとして起動し(同梱して版を固定したtypescriptパッケージのtscを tsc --lsp --stdio で起動する。この引数は公式ブログにはなく、ts-lsp-mcpなど既存ツールの使い方による)、標準入出力とUI WebViewの間をTauriのChannelで中継する。get\_diagnostics は同じセッションの診断を返す
- 音声解析、書き出し、前処理はRust側のスレッドで行い、UIスレッドに載せない
- 起動時は前回のウィンドウとワークスペースを即座に復元し、スケッチの実行はその後に始める。スケッチ用の子WebViewは、UIのWebView2環境ができてから(UIの読み込み後に)作る。UIの環境を作っている最中に別環境の子WebViewを作ると ERROR\_BUSY(0x800700AA)で失敗することがあった(フェーズ1)
- 目標値: 起動から操作可能まで1秒、UI操作60fps、保存からプレビュー反映まで100ms

**位置づけはAEとTouchDesignerの中間にある、コードで映像を定義するツールです。**

| 観点 | After Effects | TouchDesigner | このアプリ |
| --- | --- | --- | --- |
| 作り方 | レイヤーとキーフレーム | ノードをつなぐデータフロー | コード + キーフレーム・MIDIトラック |
| 時間 | タイムライン上の任意のフレームを再計算 | 実時間で流れ続ける | タイムライン上の任意のフレームを再計算 |
| 主な出力 | オフラインレンダリング | ライブ出力(VJ、インスタレーション) | オフラインレンダリング(ライブ出力は後段) |
| 得意分野 | 合成と仕上げ | 入力に反応する実時間処理 | 音・MIDI・データで駆動する生成映像 |

時間モデルと書き出しはAE、ライブ入力の扱いはTouchDesignerに倣っています。ノードエディタは作らず、処理の連結はコードと合成設定で表します。AIはノードグラフよりコードのほうを正確に書けるためです。

## 全体アーキテクチャ

Windows専用のTauriアプリとして作ります。中心はディスク上の作業フォルダ(works/ 以下の作品フォルダ)で、人はアプリ画面から、AIはファイル編集とMCPから同じフォルダを触ります。実行単位は次の3つです。

- **UI WebView**: エリア、コードエディタ、タイムライン、パラメータ。スケッチのコードは一切実行しない
- **スケッチWebView**: スケッチの実行専用。プレビュー用と書き出し用を別に持ち、UIとはプロセスを分ける。プレビュー用はUIウィンドウ内の子WebViewとしてプレビューエリアに重ねて表示する。子WebViewは別のネイティブ領域でUIのメニューやツールチップを上に描けないため、メニュー・F3検索・エリアのドラッグ中とウィンドウのリサイズ中は子WebViewを隠し(フェーズ0では、リサイズ中に子WebViewの位置合わせが1〜2フレーム遅れて隙間が見えた)、直前フレームの静止画をUI側に表示する。並列プレビューで動かすのはアクティブな1つだけにし、他は静止画にする。スケッチ用WebViewはUIと別のWebView2環境(ユーザーデータフォルダ)で作り、ブラウザプロセスとGPUプロセスも分ける(環境1つにつき約300MBのワーキングセットが増える)。書き出し用とCLI用のスケッチWebViewは、非表示(Tauriの visible(false))のウィンドウに置く。このウィンドウはページからは表示中に見え、rAFもタイマーも間引かれない。起動引数はプレビューと同じにし、データフォルダは分けて別の環境にする(フェーズ0では、プレビューと環境を共有した書き出し用ウィンドウがタイマー・Workerとも約30fpsに張り付く回があった)。書き出しの進行はrAFに頼らず、MessageChannelかPromiseの連鎖で1フレームずつ進める
- **Rustコア**: ファイル監視、スケッチのビルド、音声解析、音声再生(cpal)、MIDI入出力(midir)、MIDIファイルとDAWマーカーのパース、project.jsonの唯一の書き手と取り消し履歴、プレビューキャッシュ管理、書き出しとffmpegの管理(ffmpeg-sidecar)、MCPサーバー、ファイルの受け渡し(専用URIスキーム)と描画済みフレームの受け渡し(WebView2の共有メモリ)、時刻の配信

**スケッチWebViewとの通信**: スケッチWebViewに許可するのは次の表の通信だけです(セキュリティ上の許可リストもこの表から作る)。

| 向き | 内容 | 経路 |
| --- | --- | --- |
| Rust→スケッチ | 時刻(サンプル位置・OS時刻・フレーム番号) | Tauriイベント |
| Rust→スケッチ | params・キーフレーム・クリップの変更、コード更新通知(ビルド済みJSのURL)、ライブMIDI | Tauriイベント |
| Rust→スケッチ | アセット、解析データ、ビルド済みJS | 専用URIスキーム(fetch) |
| Rust→スケッチ | AEプラグインから届く入力レイヤーのピクセル | WebView2のSharedBuffer(共有メモリ) |
| スケッチ→Rust | 生存通知、エラー、ログ、フレーム時間、defineSketchの宣言(mode・renderer・params・tracksの型。setup成功時に送り、Rustコアが.cache/に保存してJSON Schemaを生成する) | 専用URIスキーム(POST) |
| スケッチ→Rust | キー入力(プレビューにフォーカスがあるときのショートカット。RustがUIへイベントで渡す) | 専用URIスキーム(POST) |
| スケッチ→Rust | 描画済みフレーム | SharedBuffer(共有メモリ)に書き、書き終えた通知だけを専用URIスキーム(POST)で送る。localhost HTTPとフレーム本体の専用URIスキームPOSTは許可しない(フェーズ0の4K 1枚: 共有メモリ7.7ms、localhost HTTP 160ms、専用URIスキーム328ms) |

マイクとカメラはスケッチWebView内でgetUserMediaを使い、権限要求はアプリが自動で許可します。

## スケッチの構造とランタイムAPI

**用語**: この文書では次の意味で使います。

| 用語 | 意味 |
| --- | --- |
| 作業フォルダ | 全作品を置く親フォルダ(`works/` の親)。AGENTS.md、CLAUDE.md、スキル、型定義、テンプレートを置き、全体を1つのgitリポジトリにする |
| 作品 | 1本の映像。`works/` 直下の1フォルダで、project.jsonが正。MCP・CLI・履歴・ワークスペース配置の単位 |
| スケッチ | 作品内の1つの描画コード(sketch.tsまたはISFのshader.fs)。レイヤーから参照される |
| レイヤー | スケッチをタイムライン上に置いたもの。同じスケッチを別のparamsで複数のレイヤーに使える |
| 履歴 | gitのコミット。サムネイルを紐付けて表示する |

作品は1フォルダで、中に複数のスケッチを持ちます。作品の正はルートのproject.json(解像度、fps、尺、音声、レイヤー、トラック、キーフレーム、クリップ、マーカー、イベント対応表(eventMap)、版番号)で、各スケッチはコードとparamsの既定値だけを持ちます。思いつきを試すときは「スケッチ1つだけの作品」で始め、レイヤーを足せばそのまま作品になります。プリコンポーズは別作品のproject.jsonを相対パスで参照し、循環参照は読み込み時に検出してエラーにします。AIも人もこのフォルダだけを触ればよく、アプリ本体には手を入れません。

```
works/mv-song/
  project.json       作品の正(解像度・fps・尺・音声・レイヤー・トラック・キーフレーム・クリップ・マーカー・イベント対応表(eventMap)・版番号)
  assets/            音声・MIDI・画像・動画・CSVなど
  sketches/
    rain-lines/
      sketch.ts      描画コード
      params.json    paramsの既定値
    bg-noise/
      shader.fs      ISFシェーダー
    words/
      sketch.ts      クリップの文字を描く(最小の例)
  .cache/            解析結果・動画プロキシ・プレビューキャッシュ(gitに入れない)
  renders/           書き出し先(gitに入れない)
  .gitignore         .cache、renders、100MBを超えるアセットを除外
```

変更履歴とサムネイルはgitで管理し(サムネイルはコミットに紐付けて `.cache/` に置く)、別のスナップショットフォルダは持ちません。

描画関数は「前フレームの状態」ではなく「時刻t」を受け取ります。これにより任意の時刻へのシークと、プレビューと書き出しで同一の結果が保証されます。

```ts
import { defineSketch } from "@sketchbench/runtime";

export default defineSketch({
  mode: "pure",
  renderer: "canvas2d",            // "webgl" | "three" | "shader" | "p5" | "html" | "hydra"
  params: {
    density: { type: "float", min: 0, max: 1, default: 0.4 },
    color:   { type: "color", default: "#9fd3ff" },
  },
  async setup({ assets }) {
    return {
      song: await assets.audio("song.wav"),   // 解析済みの音声
      midi: await assets.midi("drums.mid"),
    };
  },
  draw({ g, t, frame, width, height, p, rand }, { song, midi }) {
    const kick = midi.envelope({ note: 36 }, t, { decay: 0.25 });
    const low  = song.band("low", t);
    // p.density はスライダーとキーフレームで動く
  },
});
```

| API | 内容 |
| --- | --- |
| `t` / `frame` | 秒とフレーム番号。書き出し時も同じ値 |
| `p` | params宣言から自動生成されたUIとタイムラインの合成値 |
| `rand` | シード固定の乱数とノイズ。`Math.random`とcrypto.getRandomValuesもスケッチWebViewでは差し替える。純粋スケッチでは毎フレーム「シードとフレーム番号」から乱数を初期化するので順不同に描いても同じ結果になり、状態あり・逐次スケッチは先頭か保存点から再生したときに同じ結果になる |
| `g` | 選んだrendererのコンテキスト(Canvas2D、WebGL2、three.jsのscene、p5インスタンス) |
| `simulate(step)` | 粒子や物理など状態を持つ表現用。固定タイムステップで進め、一定フレームごとに状態を保存してシーク時は直前の保存点から再計算する |
| mode / renderer / params | defineSketchの宣言。paramsとtracksのフィールドの型はfloat、int、bool、color、vec2、enum、text、file、curve、list\<text>。ISFのshader.fsは置くだけでrendererがshader、modeがpure(PERSISTENTバッファを使う場合はstateful)になり、sketch.tsは不要 |
| setup / draw / dispose | setupは読み込み時とコード変更時に1回で、戻り値はdrawの第2引数に渡る。drawはフレームごと。disposeはホットリロード前と終了時に呼ばれ、イベントやGPU資源を解放する |
| assets.audio / midi / video / font / data | 解析済みの素材。song.rms(t)・band・beat、midi.notesAt(t)・cc・envelope、video.frameAt(t)など時刻で引く関数を持つ |
| events / section / beats / inputs | 名前付きイベント(events.since)、区間内の進捗(section)、拍単位の時刻(beats)、他レイヤーの描画結果(inputs.layer) |
| tracks | GUIで作るクリップトラック。宣言した型のフィールドを持ち、at(t) で有効なクリップをすべて返す(「タイムライン」節) |
| width / height | 出力解像度(レイヤーの内部解像度を反映した値) |

最小の例(フェーズ1〜2の実装の基準にする。tracksとaudioはフェーズ2で実装する):

```ts
// works/mv-song/sketches/words/sketch.ts
import { defineSketch } from "@sketchbench/runtime";

export default defineSketch({
  mode: "pure",
  renderer: "canvas2d",
  params: { size: { type: "float", default: 96, min: 8, max: 400 } },
  tracks: { words: { fields: { text: "text", color: "color" }, tail: 0.5 } },
  draw({ g, t, p, tracks, width, height }) {
    g.clearRect(0, 0, width, height);
    for (const c of tracks.words.at(t)) {
      g.globalAlpha = 1 - c.after / 0.5;   // 終了後はフェード
      g.fillStyle = c.value.color;
      g.font = `${p.size * (1 + c.progress * 0.2)}px sans-serif`;
      g.fillText(c.value.text, width / 2, height / 2 + c.index * 4);
    }
  },
});
```

時刻はproject.jsonではフレーム番号、スケッチへは秒で渡します。クリップはidをキーにして保存します。正確な形式はJSON Schemaと.d.tsを正とし、この例はその概形です。

`renderer: "shader"` はフラグメントシェーダー1枚だけで動くモードで、`TIME`、音声帯域、MIDIエンベロープ、paramsが自動でuniformになります(ISF形式では時刻は標準のTIME・TIMEDELTA・FRAMEINDEX、音声は標準のaudio・audioFFT入力、MIDIと独自データは sb\_ を付けたfloat入力として宣言する)。`"p5"` は既存のp5.jsコードをインスタンスモードで持ち込む互換層です。

`"html"` はHTML/CSSの要素を時刻tで動かし、画像にしてレイヤーとして使うモードです(Canvas系より書き出しは遅い)。98.cssのようなUIライブラリやブラウザの文字組みを映像に使えます。画像化の第一候補は、ChromiumのHTML-in-Canvas API(drawElementImage、WebGLのtexElementSubImage2D。オリジントライアル中。トークンは公開オリジン向けなので使わず、スケッチ用WebView2の起動引数に --enable-features=CanvasDrawElement を加える(ChromiumのFinch機能名。HyperFramesも書き出し時に同じ指定をしている)。フェーズ0ではWebView2 157で、この指定のない環境でも使えた。1080pの要素を描いて約6msで、アルファも残り、描画後のcanvasも読める。API名と対象要素の指定(canvasの子要素にし、属性はlayoutsubtreeからcontent="drawable"に変更)はChromium 150・155で変わったので機能検出で分岐し、ランタイムの更新で消える場合に備えてforeignObject方式を常に代替として保つ)です。使えない場合は、DOMをSVGのforeignObjectに入れてcanvasへ描く方式(html-to-imageなどと同じ仕組み)にします。同じスケッチWebView内で完結し、アルファも保てます。SVGはdata URLで読み込みます(フェーズ0では、blob URLで読むとcanvasがtaintされてピクセルを読めなかった)。SVG内から外部URLの画像やフォントは読まれないため、data URLとして事前に埋め込みます(文書側で読み込んだフォントも使われない)。表現できないCSSがある場合だけ、別の隠しWebViewに表示してWebView2の画面取り込み(CapturePreview。アルファなし、1080pで1回約270ms)で取り込み、専用URIスキーム経由で合成側に渡します。非表示や最小化のウィンドウでも取り込めます。CSSアニメーションとトランジションは、毎フレーム document.getAnimations() を一時停止して currentTime を時刻tに合わせて動かし、GSAPは timeline.seek(t) で動かします(HyperFramesのシークの実装を参考にする)。`"hydra"` はライブコーディング用の映像シンセHydraを、時刻を外から与えて動かすモードで、他のレンダラーの出力を入力に取れます。

**既存コードを決定的に動かす仮想時計**: p5.jsのdrawループ、three.jsのClock、GSAP、Hydraはブラウザの時計とrequestAnimationFrameで動くため、そのままではプレビューと書き出しで結果がずれます。スケッチWebViewには[timeweb](https://github.com/tungs/timeweb)と同じ方式の仮想時計を最初に読み込み、`Date.now`、`performance.now`、`requestAnimationFrame`、`setTimeout`、`setInterval` を差し替えます。ランタイムが1フレーム分時刻を進めるたびに待機中のコールバックを実行するので、時刻tで書かれていないコードも書き出し時に同じ結果になります。ランタイム自身が使うライブラリ(書き出しのMediabunnyなど)は内部でタイマーを使うことがあるため、フレームの合間(スケッチのコードが動いていないとき)だけ本物のタイマーに戻して呼ぶ。この方式は時刻を戻せないため、こうしたコードのシークは先頭か保存点からの再実行になります。Hydraは `autoLoop: false` と `tick(dt)`、p5は `noLoop()` と `redraw()` で直接駆動します。timewebと同じく、`event.timeStamp` とWeb AudioのAnalyserNodeは仮想時計に従わないため、音への反応は必ず事前解析データを使います。

**スケッチの3分類**: スケッチは `defineSketch` の `mode` で次のどれかを宣言します。静的な解析では状態の有無を判定できないため、宣言は決定性テスト(時刻を順不同に描いてハッシュが一致するか)で検証し、食い違えば診断で知らせます。宣言がない場合は「逐次」として扱います。

| 機能 | 純粋(`pure`: 時刻tの関数) | 状態あり(`stateful`: simulateやフィードバック) | 逐次(`sequential`: 仮想時計で動かす既存コード) |
| --- | --- | --- | --- |
| 任意時刻へのシーク | 即座 | 直前の保存点から再計算 | 先頭か保存点から再実行 |
| プレビューでのフレームスキップ | 可 | 不可(固定ステップで進める) | 不可 |
| モーションブラー | 可(1フレーム内の複数時刻を描画) | 可(サブステップを保存して合成) | 不可(高fpsで書き出して後で合成する方式のみ) |
| 書き出しの中断再開 | 可 | 保存点から可 | 保存点から可 |
| 並列書き出し | 可 | 保存点ごとに区間を分けて可 | 不可 |
| AEプラグイン | 可 | 可(初回は保存点の計算で遅い) | 不可 |

ランタイムは差し替え前の本物のrequestAnimationFrameを保持し、プレビューの描画ペースに使います。状態あり・逐次スケッチの描画が間に合わないときは音声を止めて仮想時刻だけを進め、音と合わせて通しで確認したいときはプレビューキャッシュで再生します。フォントはFontFace APIで読み込み、setupの前に document.fonts.ready を待ちます。システムフォントも作品にファイルとしてコピーし、内容ハッシュをキャッシュのキーに含めます。

**ビルドとライブラリ**: sketch.tsはRust側のOxcでJSに変換し、依存はバンドルせず、ブラウザのネイティブESMとimport mapで読み込みます(解決はoxc\_resolverで行い、import mapをRust側で生成する。RolldownのRustクレートは外部からの利用をサポートしていないため使わない)。ブラウザはpackage.jsonのexportsを解釈しないので、推移的な依存とexportsのサブパス(条件はbrowser→import→default)はRust側でoxc\_parserにより全走査してimport mapへ個別に展開し、版が衝突する依存はscopesで分けます。CSS・JSONのimportは属性付きに書き換え、process.envは定数に置き換えます。import mapは後から張り替えられないため、依存を変えたらスケッチWebViewを再読み込みし、変換できないパッケージは診断で知らせます。作業フォルダのルートにはtsconfig.json(module: esnext、moduleResolution: bundler、noEmit)を置き、同梱ライブラリとランタイムの.d.tsをpathsで割り当てます。内蔵の言語サーバーとVS Codeは同じtsconfigを読みます。three.js、p5.js、Hydra、GSAPなどよく使うライブラリは版を固定してアプリに同梱し、オフラインでも使えるようにします。それ以外はESM形式のパッケージに限り、作品ルートのpackage.jsonに書くと同梱のpnpmを --ignore-scripts 付きで実行して取得します(postinstallは実行せず、CJS専用のパッケージは対象外)。コード変更時は \`dispose()\` を呼んでから \`setup()\` を再実行し、paramsの値とタイムライン位置は保ちます。rendererの種類が変わらない限りWebGLコンテキストは使い回し、アセットはファイルが変わったときだけ読み直します。コード変更時はあわせて`simulate` の保存点を破棄します。

**p5.jsの版**: 現行のp5.js 2.x(`async setup`)を既定にし、AIが1.x流の `preload()` を書いても動くよう公式の互換アドオン([p5.js-compatibility](https://github.com/processing/p5.js-compatibility))を読み込みます。

**シェーダーモードはISF形式**: `renderer: "shader"` のファイルは[ISF](https://github.com/mrRay/ISF_Spec)(GLSLの先頭にJSONで入力とパスを書く形式)で保存します。入力はそのままパラメータUIになり、同じファイルをVDMXやResolumeでも使えます(sb\_ 入力はそちらでは手動のスライダーになる)。ISF4AEで使えるのは、audio入力と永続バッファを使わないファイルに限ります。エフェクトチェーン(次節)もISFで書きます。

## 合成とレイヤー

1つの作品は複数のレイヤーを重ねて作ります。合成はスケッチWebView内のGPUで行い、各レイヤーの描画結果をテクスチャとして受け渡します。

| 要素 | 内容 |
| --- | --- |
| レイヤー | スケッチ1つの出力。開始・終了時刻、不透明度、ブレンドモード(通常・加算・乗算・スクリーン・差分)、時間オフセットと速度、位置・スケール・回転・アンカー(キーフレーム可)を持つ |
| エフェクトチェーン | レイヤーごとにISFシェーダーを順にかける(ブルーム、色収差、グレインなど) |
| 入力の受け渡し | `inputs.layer("bg")` で他レイヤーの描画結果をテクスチャとして参照する。動画素材も同じ扱い |
| プリコンポーズ | レイヤー群を1つのレイヤーにまとめ、別の作品から参照する |
| 内部解像度 | レイヤーごとに変えられる(重い背景だけ半分の解像度で描くなど) |
| フィードバック | 前フレームを参照する効果は `simulate` と同じ保存点方式で扱い、シークと書き出しの結果を揃える |
| トラックマット | 上のレイヤーのアルファまたは輝度でこのレイヤーを切り抜く |

合成設定はproject.jsonに保存し、タイムラインのレイヤートラックで編集します。ノードエディタは持たず、複雑な処理の連結は1つのスケッチ内の複数パスとしてコードで書きます。

## 時間モデルとタイムライン

時間の正は1本のマスタークロックです。時刻は浮動小数ではなくフレーム番号と有理数のfps(30000/1001など)で保持し、長尺でも誤差がたまりません。プレビューでは音声の再生位置がクロックを駆動し、描画が間に合わないフレームは飛ばします(キャッシュ済みの区間は実時間で再生)。書き出しでは `frame / fps` でクロックを進めるので、描画が重くてもコマ落ちしません。音声の再生はRust側(cpal)で行い、その再生位置をUIとスケッチの両WebViewに配信します。シーク中は音声を短い断片で再生し(スクラブ)、位置を耳で確認できるようにします。

**時刻の配信**: Rust側は再生中、60Hzで「サンプル位置・サンプルレート・その瞬間のOS時刻」を両WebViewに送ります。各WebViewは受信したOS時刻と自分の時計の差で現在位置を補間し、音声出力の遅延(cpalから取得)と描画から表示までの1フレーム分を差し引いて描画する時刻を決めます。UIとスケッチのフレーム番号が食い違った場合はRust側の値を正とし、停止中とシーク中はフレーム番号を直接送ります。スケッチWebViewではperformance.nowが仮想時計に置き換わるため、ランタイムは差し替え前のperformance.nowとperformance.timeOriginを保持して補間に使います。Rust側はUNIX時刻(GetSystemTimePreciseAsFileTime)を送り、JS側はtimeOrigin + performance.nowと比べ、起動時と10秒ごとに往復時間を測ってずれを補正します。音声出力の遅延はcpalのコールバック時刻と再生時刻の差から求めます。

| トラック | 中身 | コードからの参照 |
| --- | --- | --- |
| 音声 | 波形表示、ビート・オンセットのマーカー | `song.rms(t)` `song.band("low", t)` `song.beat(t)` |
| MIDI | ピアノロール、CCカーブ | `midi.notesAt(t)` `midi.cc(1, t)` `midi.envelope(...)` |
| パラメータ | paramsごとのキーフレームとイージング | `p.density`(自動で評価済み) |
| マーカー・区間 | 「intro」「drop」など名前付き区間 | `section("drop", t)` → 区間内の0〜1 |
| レイヤー | 複数スケッチの開始・終了と合成順 | 合成設定で参照 |
| クリップ | 宣言した型のフィールドを持つ区間の列(「GUIで作るデータとコードの対応」) | tracks.<名前>.at(t) |

キーフレームとマーカーは `project.json` に保存します。AIが「サビで密度を1.0に」のような指示をJSON編集で実行でき、人はタイムライン上で同じものをドラッグで直せます。BPMを設定すると小節グリッドと `beats(t)`(拍単位の時刻)が使えます。

**GUIで作るデータとコードの対応**: 「どの時刻に、何を」のようにコードだけでは扱いにくい内容はGUIで作り、コードはそれを読むだけにします。仕組みは1つで、スケッチが入力の型を宣言すると、その型に合う編集UIが自動で作られます。特定の用途(歌詞など)専用の形式は持ちません。

- **params(値)**: 数値・色・文字列・真偽・選択肢・アセット・2D点・カーブ・文字列のリスト(型名はfloat、int、bool、color、vec2、enum、text、file、curve、list\<text>)。パネルに入力欄が出て、数値系はキーフレーム、それ以外は時刻ごとの切り替え(ホールド)を打てます。
- **tracks(クリップトラック)**: 時間区間(クリップ)の列で、各クリップがparamsと同じ型のフィールドを持ちます。`tracks: { words: { fields: { text: "text", size: "float", color: "color" }, tail: 0.5 } }` のように宣言するとタイムラインにトラックが出て、クリップの配置・伸縮・分割・拍への吸着と、インスペクタでのフィールド編集ができます。クリップ内の各フィールドにもキーフレームを打てます。
- **一括入力**: 改行区切りテキストやCSVの貼り付け(1行を1クリップにする)、再生中のキー入力による区切り打ち、マーカー・MIDIノート・ビート解析・ボーカル合成ファイルからの変換を用意します。どれも結果は通常のクリップになり、後から手で直せます。
- **コードからの参照**: `tracks.words.at(t)` は時刻tに有効なクリップをすべて返し、各クリップからフィールドの値(value)、クリップ内の経過時間(elapsed、秒)、進捗(progress、0〜1)、通し番号(index)、終了後の経過時間(after、秒。終了前は0)が取れます(宣言で `tail` を指定すると、終了後もその秒数だけ返る)。同じ処理をクリップごとに呼べば、切り替わるたびに繰り返す表現も、前のものを残して重ねていく表現も書けます。時刻とデータだけで結果が決まるため、純粋スケッチのまま使え、シークや並列書き出しでも結果は変わりません。クリップの時刻は作品時刻で保存します。スケッチが受け取るtはレイヤー時刻(時間オフセットと速度を適用した後)で、at(t)はランタイムがtを作品時刻に戻してクリップを引きます。音声・MIDI・マーカー・events・section・beatsも同じく作品時刻で引き、video.frameAtとframe、randのシードはレイヤー時刻を使います。paramsのキーフレームはレイヤー時刻で、クリップ内のキーフレームはクリップ開始からの相対フレームで保存します(クリップを動かすとキーも一緒に動く)。同じトラック内の重なりは許し、at(t)は開始時刻順(同時なら作成順)に返します。
- **型の変更とAI**: 宣言を変えても既存の値は残し、型が合わなくなった項目は診断で知らせます。値はproject.jsonに保存され、宣言からJSON Schemaが作られるので、AIはMCPかJSON編集で同じデータを作れ、人はGUIで直せます。各クリップは作成時に不変のidを持ち(追加はidなしで送り、Rustコアが採番して返す。JSONの直接編集でidのないクリップが入った場合も、取り込み時に採番して書き戻す)、project.jsonではidをキーにして保存します。差分の合成、取り消し、診断はidで指し、通し番号は開始時刻順に毎回数え直す値として保存しません。一括入力1回は取り消し1単位です。スキーマは最後に正常に読み込めた宣言から作って.cache/に保持し、コードが壊れている間もその版で検証します。

## 外部入力

ファイル入力はすべて「読み込み時に一度だけ解析し、時刻tで引けるデータにする」方針です。リアルタイムのAnalyserNodeに頼ると、シークや書き出しで値がずれるためです。解析結果は `.cache/` に保存し、ファイルが変わるまで再利用します。

| 入力 | 事前処理 | 取り出せるもの |
| --- | --- | --- |
| 音声(wav/mp3/flac) | フレーム単位のFFT、RMS、帯域別エネルギー、オンセット、テンポ推定 | スペクトラム、帯域値、ビート、波形サンプル |
| ステム(複数音声) | ファイルごとに上と同じ解析 | ドラムだけで反応、などの分離した制御 |
| MIDI(.mid) | ノートとCCを秒単位に変換 | 発音中ノート、ベロシティ、CC値、ADSR式のエンベロープ、名前付きイベント |
| ボーカル合成のプロジェクト(.svp/.vsqx/.ustx) | ノート、歌詞、音素を時刻に変換 | 現在の歌詞、モーラ、母音の種類 |
| DAWのマーカー(REAPERの.rppなど) | マーカーと範囲を抽出 | タイムラインのマーカー・区間 |
| 動画(mp4/mov) | WebCodecsでフレーム正確にデコード | `video.frameAt(t)` をテクスチャやピクセル配列として取得 |
| 画像・SVG・フォント | そのまま読み込み | テクスチャ、パス、文字幅の計測、グリフのアウトラインと点列 |
| CSV/JSON/SRT | パース | データ配列、時刻付き歌詞・字幕 |

MIDIは音符の可視化だけでなく、演出イベントの入力にも使います。「ノート36=ブロック登場、ノート38=反転、ベロシティ=強さ」のような対応表を `project.json` に持ち、コードからは `events.since("block_appear", t)` のように名前で参照します。対応表はUIで編集でき、作業中に割り当てを変えてもコードは書き換えずに済みます。DAWで拍に合わせて演出を打ち込み、アプリ側はその結果を描くだけ、という分担ができます。

ライブ入力としてMIDIコントローラー(Rust側のmidirで受信)、マイク、カメラも受け付けます。ライブ入力は「録音」ボタンでタイムライン上のトラックへ書き込み、以降はファイル入力と同じ扱いにします。フェーダーをMIDIコントローラーに割り当てて動かし、その動きをキーフレームとして残す使い方ができます。

解析はRust側で行います。デコードはSymphonia、FFTはrustfft、特徴量(RMS・帯域・オンセット)は自前実装、ビートとダウンビートはBeat This!のRust移植であるbeat-thisクレート(MIT。22050Hzモノラル化とメルスペクトログラムの前処理、ONNXモデルの実行、ピーク検出による後処理を含み、既定では純Rustのrtenで動く)を使います。DBNによる後処理は含まれません。フェーズ0で、beat-this 1.1.0(rten)がWindowsで動き、Python版の出力と拍・ダウンビートともにF値1.0(±70ms)で一致することを確かめました。モデル(mel\_spectrogram.onnxと、フル精度のbeat\_this.onnx約83MB)はクレートに含まれないため、作者リポジトリから取得して同梱します。打ち込みのクリックのような楽曲らしくない音ではダウンビートを出しすぎることがあるので、拍子と1拍目はタイムラインで直せるようにします。ボーカル合成の形式はUI WebViewのWorkerでutaformatix-tsが読み込み、モーラ単位の歌詞データ(文字、開始・終了時刻、母音)に変換します。

パイプラインの前段には「前処理器」を足せます。前処理器は入力ファイルを受け取り `.cache/` に結果を書く外部コマンドで、初回使用時にモデルを取得する任意機能として音源分離(demucs-onnxを呼ぶ外部コマンド。Python 3.11以上が必要で、モデルは単体のhtdemucs(約316MB)を既定にし、配布物には含めない。ドラムだけ・ボーカルだけのステムを作る)を用意します。オプティカルフローや深度推定などPython製のツールも同じ形で接続できます。

**動画素材**: WebCodecsでデコードできないProResやDNxHRなどの中間コーデックと、可変フレームレートの素材は、読み込み時にffmpegで固定フレームレートのプロキシに変換して `.cache/` に置きます。プレビューも書き出しもプロキシを使い、元素材は変更しません。長尺の動画は必要な区間だけをデコードし、保持するフレーム数に上限を設けます。動画内の音声は音声トラックとして切り出します。アルファ付きの素材はH.264のプロキシではアルファが失われるため、可逆圧縮の連番(QOIなど)をプロキシにします。連番画像(PNG・EXR)も動画素材と同じAPIで読み込め、開始フレーム番号とfpsを指定して時刻に対応させます(EXRはexrクレートで読む)。

## 書き出しパイプライン

書き出しは実時間録画ではなくオフラインレンダリングです。1フレームずつ時刻を進めて描画し、完了を待ってから次へ進むので、4Kや重いシェーダーでも欠落しません。

1. 範囲(全体・区間・ループ範囲)、解像度倍率、形式を選ぶ。プレビューは0.5倍、書き出しは等倍や2倍と分けられる
2. 各フレームを描画し、キャンバスをVideoFrameとして取り出す
3. 形式に応じてエンコードする(下表)
4. 音声トラックを尺に合わせて切り出し、動画に多重化する
5. `renders/` に「作品名\_日時\_コミットID」の名前で保存する(上書きしない)

| 形式 | 経路 | 用途 |
| --- | --- | --- |
| MP4 (H.264。AV1はGPUが対応していれば。H.265はWebView2のWebCodecsで使えないためffmpeg経由) | スケッチWebView内のWebCodecs + Mediabunnyで映像だけのMP4を作り、音声はRustコアがffmpegで多重化 | SNS投稿、確認用。サーバー不要で速い |
| 連番PNG / EXR | フレームを共有メモリでRustコアへ渡して書き込み | AE、DaVinci、Blenderでの合成 |
| ProRes 4444(アルファ付き) | PNG・EXRと同じ経路でRustコアへ渡し、Rustコアが起動するffmpegにパイプ | 編集ソフトでの重ね合わせ |
| GIF / WebM | ffmpeg | 短いループ素材 |

同じ処理をCLIでも実行できます(`sb render works/mv-song --from 8 --to 16 --scale 2 --format prores`)。アプリの非表示ウィンドウで実行するため、AIが書き出しまで自動で行え、複数パラメータの総当たり書き出しもスクリプトで組めます。

**フレームの受け渡し**: TauriのIPCは大きなバイナリの転送が遅く、Windowsで10MBに約200msかかったという非公式の計測があります([tauri#11915](https://github.com/orgs/tauri-apps/discussions/11915))。4Kの非圧縮フレームは1枚約33MBなので、通常のIPCで毎フレーム送る方式は採りません。MP4などの圧縮形式はWebView内でWebCodecs(ハードウェアエンコード)とMediabunnyで映像だけのファイルを作り、音声は後でRust側で多重化します。PNG・EXR・ProResのように非圧縮フレームが要る形式は、Rust側が確保したWebView2の共有メモリ(PostSharedBufferToScriptで読み書き可として渡す)にスケッチWebViewが直接書き込み、書き終えたら専用URIスキームへの短いPOSTで通知します。共有メモリはスケッチWebView側のWebView2環境で作り(CreateSharedBuffer)、書き出し開始時に数枚分を1回だけ渡して使い回し、終了時に chrome.webview.releaseBuffer で解放します。WebGLの readPixels は共有メモリのビューへ直接書けます。フェーズ0で4K RGBA8 1枚の往復を比べた結果、共有メモリ(書き込み、通知、Rust側での別バッファへのコピーまで)が中央値7.7ms、トークン認証付きのlocalhost HTTP(axum)が160ms、Tauriの非同期カスタムURIスキームへのPOSTが328msでした。共有メモリだけを採用し、他の2方式はフレーム転送に使いません。H.264で扱える解像度はプロファイル・レベルとGPUのエンコーダーで決まるため、書き出し前にWebCodecsで設定を試し、通らなければAV1かffmpeg経由に自動で切り替えます(WebView2 157のWebCodecsはH.265のエンコードに対応していなかった。VP9はソフトウェアのみ)。

**画質設定**: 色深度、アルファの種類(ストレートとプリマルチプライド)、モーションブラー、スーパーサンプリングを指定できます。対応する色深度はレンダラーで違います。

| レンダラー | 内部の色深度 | 書き出せる色深度 |
| --- | --- | --- |
| WebGL2・three.js・ISF・Hydra | 16bit浮動小数テクスチャ | 8bit、16bit、32bit浮動小数(EXR) |
| Canvas2D・p5の2Dモード | 8bit | 8bit(合成時に16bitへ変換して他レイヤーと重ねる) |
| HTML | 8bit(HTML-in-Canvas方式とforeignObject方式はアルファあり、画面取り込み方式はアルファなし) | 8bit |

合成は16bit浮動小数で行い、8bitで書き出すときにディザをかけます。WebCodecsのVideoEncoderの設定には色の指定がないため、RGBからYUV(NV12)への変換はスケッチWebView内のシェーダーで行い(色深度とアルファを扱うフェーズ4から。フェーズ1は出力canvasをMediabunnyのCanvasSourceでRGBのまま渡し、フェーズ0で確かめたエンコーダー側のBT.709リミテッド変換に任せる)、colorSpace(BT.709の原色・伝達特性・行列とレンジ)を明示したVideoFrameとしてエンコーダーに渡します(フェーズ0の環境ではRGBを直接渡してもBT.709リミテッドに変換されたが、エンコーダーの実装に依存するため自前で変換する)。フェーズ0では、WebCodecsが出力したH.264のVUIに色情報(video\_signal\_type)が入らず、colorSpaceはdecoderConfigのメタデータにしか反映されないことを確かめました。ビットストリーム内の色情報(VUI)は、音声を多重化するときにffmpegのビットストリームフィルター(h264\_metadata・hevc\_metadata)で再エンコードせずに書き込みます。色を厳密に決めたい書き出し(BT.709・リミテッドレンジやフルレンジの指定)は、RGBフレームをffmpegに渡してエンコードする経路を選べます。ffmpeg経由のH.264・H.265は、LGPLビルドで使えるハードウェアエンコーダー(Media Foundation、NVENC、Quick Sync、AMF)を使い、libx264・libx265は使いません。色情報がないと、再生ソフトごとにガンマや色がずれます。

他ソフトで仕上げる前提で、映像と一緒にタイミングデータも書き出します。マーカーとイベントを、AE用のJSXスクリプト(マーカー付きのレイヤーを生成)とBlender用のPythonスクリプト(キーフレームを生成)として出力し、仕上げ側で同じタイミングを使えるようにします。

**音声の書き出し**: 音声の処理はRust側に一本化します。音声トラックごとの音量とフェードを適用してミックスし、48kHzにリサンプルして、MP4はAAC、ProRes(MOV)はPCMで書き出します。映像との多重化はffmpegで映像を再エンコードせずに行います。

**失敗時の扱い**: 書き出しは一時ファイルに書いてから最後に名前を変えるので、失敗しても壊れたファイルは残りません。ファイル名は「作品名\_日時\_コミットID.拡張子」で上書きしません。開始前に必要なディスク容量を見積もって足りなければ始めず、ffmpegの異常終了や描画例外はそのフレーム番号とログを添えてレンダーキューに表示します。連番画像は書き終えたフレームまで残し、続きから再開できます。

## 映像制作ソフトとしての要件

生成と書き出し以外に、本番制作で欠けると困る項目とその対応です。

| 要件 | 設計での対応 |
| --- | --- |
| フレームレート | 23.976、29.97などNTSC系を有理数で保持し、長尺でも音とずれないようにする。タイムコード表示 |
| 色管理 | 作業色空間(sRGB、リニア)と出力(Rec.709、sRGB)を指定。内部は16bit浮動小数のバッファで描画し、8bit化の際にディザをかけてバンディングを防ぐ |
| アルファ | ストレートかプリマルチプライドかを明示し、ProRes 4444・PNG・EXRへ正しく渡す |
| 音との同期 | 48kHz基準でサンプル単位に同期。音声のオフセット設定 |
| 重いスケッチの再生 | 描画済みフレームをRAMとディスクにキャッシュして実時間で再生する(AEのプレビューキャッシュに相当)。プレビュー解像度と書き出し品質を分ける |
| 長時間の書き出し | レンダーキュー、バックグラウンド実行、進捗と残り時間の表示、中断した位置からの再開 |
| プロジェクト管理 | 自動保存、取り消しとやり直し、クラッシュ復旧、相対パス、リンク切れアセットの再リンク、素材の収集 |
| 再現性 | 乱数シードを固定し、時刻以外の外部状態を使わない。GPUの違いによる微小な差は許容する |
| 文字 | フォントの読み込み、文字幅の計測、縦書き、ルビ |
| ループ素材 | ループ区間の継ぎ目を確認する表示(先頭と末尾フレームの差分) |
| 他ソフトとの受け渡し | 連番、ProRes、タイミングデータのスクリプト(前節)、AEプラグイン(後述) |
| ライブ用途 | 全画面出力、Spout/NDI出力、ライブMIDI・音声入力(後段) |
| ラウドネス | ミックスのLUFSとトゥルーピークを表示し、書き出し時に目標値(例: -14 LUFS)へ正規化する。リミッター付き |
| 複数仕様の書き出し | 16:9と9:16など解像度・セーフエリア違いの書き出しをレンダーキューに一括登録する |

通常のWebView2(Evergreen版)はランタイム自体が自動更新されるため、更新で描画結果が変わる可能性があります。本番用にWebView2の固定バージョン配布(Fixed Version)を任意で使えるようにし(配布サイズが大きく増えるので既定はEvergreen)、書き出し時には使ったランタイムと同梱ライブラリの版を `renders/` の記録に残します。

**キャッシュの規則**: キャッシュは入力のハッシュで無効化します。

| キャッシュ | キー(これが変わると作り直す) | 上限 |
| --- | --- | --- |
| 音声解析・動画プロキシ | アセットの内容ハッシュ、解析設定、解析器の版 | 作品ごとに設定(既定10GB)。古いものから削除 |
| レイヤー単位のプレビューキャッシュ | そのレイヤーのスケッチのコードハッシュ、paramsとキーフレーム、クリップトラックの内容(変更は下記の時間範囲だけを無効にする)、参照アセットのハッシュ、`inputs.layer` で参照する上流レイヤーのキー、ランタイムと同梱ライブラリの版、プレビュー解像度 | RAMは既定2GB、ディスクは既定20GB。ディスクでは可逆圧縮(QOIなど)。古いものから削除 |
| 合成後のフレーム | 全レイヤーのキーと合成設定 | 上と共通の上限内 |
| 保存点(状態あり・逐次スケッチ) | レイヤー単位のキーと同じ | 既定は2秒ごと。スケッチごとのメモリ上限(既定256MB)を超えたら間隔を広げる |

純粋スケッチでキーフレームを動かした場合は、そのキーフレームが影響する時間範囲だけを捨てます。クリップ(内部のキーフレームを含む)を変えた場合は、変更前後のクリップの開始から終了+tailまでだけを捨てます。追加・削除・並べ替えで通し番号が変わる場合は、影響する最初のクリップの開始時刻以降をすべて捨てます。状態あり・逐次スケッチでは、変更した時刻以降のキャッシュと保存点をすべて捨てます。上流レイヤーが無効になれば、それを参照するレイヤーも連鎖して無効になります。

**その他の要件**

- タイムコードは29.97fpsでドロップフレーム表記を選べるようにする
- 縦書きとルビはCanvas2Dに機能がないため、ランタイムの文字モジュールで組版する(HTMLレンダラーではCSSの縦書きも使える)
- WebGLコンテキストはレンダラーの種類(three.js、p5、Hydra、ISF)ごとに1つ持ち、同じ種類のレイヤーで共有する(three.jsは renderer.resetState() で状態を戻す)。合成用コンテキストへはcanvasからテクスチャへのコピー(texImage2D)で渡す(フェーズ0の計測で4K 1枚約2.5ms。RGBA8・RGBA16Fとも)。Chromiumのコンテキスト数の上限(デスクトップで16。フェーズ0でもメインスレッド16・Workerは4を確認。超えると古いものから失われる。起動引数 --max-active-webgl-contexts で変えられるが、既定値のまま動く設計にする)を考え、12を超えたら表示区間外のコンテキストから解放する
- AEプラグインではAEの8・16・32bpcに合わせてピクセルを受け渡す

## AI連携

AIは「書く→実行する→結果を見る→直す」を人の手を介さず回せる必要があります。そのためにアプリ側が用意するものは次の3つです。

- **API仕様書**: 作業フォルダの `AGENTS.md`(Claude Code向けに `CLAUDE.md` も同内容)にランタイムAPI、推奨事項(`Math.random` と `Date.now` より引数の t と rand を使う等。どちらも差し替え済みで結果は揃うが、意図が読みやすくなる)、テンプレート一覧を書く。型定義(`.d.ts`)も同梱し、AIが型を読んで正しい呼び出しを書けるようにする
- **MCPサーバー**: Rustコアが公開するツール群(公式Rust SDKのrmcpで実装)(下表)
- **ファイル監視**: AIが `sketch.ts` を保存した瞬間にプレビューが更新され、人は画面でそれを見ているだけでよい

| MCPツール | 動作 |
| --- | --- |
| `create_work(template, name) / add_sketch(work, template)` | テンプレートから作品を作る、または作品にスケッチとレイヤーを足す |
| `render_frames(work, times[], layers?)` | 指定時刻のPNGを返す。AIが見た目を確認する主経路 |
| `render_contact_sheet(work, from, to, n)` | 区間をn枚並べた1枚画像。動きの確認用 |
| `get_diagnostics(work)` | コンパイルエラー、実行時例外、フレーム時間(ms) |
| `inspect_asset(path)` | 音声のBPM・オンセット一覧、MIDIのノート範囲などをテキストで返す |
| `set_params` / `set_keyframes` | project.jsonを安全に編集する |
| `export(work, options)` | 書き出しを実行しパスを返す |
| list\_works() / get\_work(work) / list\_templates() | 作品一覧、project.jsonの現在値、テンプレート一覧を返す |
| set\_layers(work, layers) / set\_event\_map(work, map) | レイヤー構成と合成設定、イベント対応表を書き換える(JSON Schemaで検証) |
| restore\_history(work, commit) | 作品を指定したコミットの状態に戻す(破壊的操作の注釈を付ける) |
| get\_tracks(work, layer) / set\_clips(work, layer, track, clips) | クリップトラックを読み書きする。get\_tracksは値と型定義を返し、set\_clipsはidを指定した追加・更新・削除の差分を受け取る(全置換はreplace: trueのときだけで、破壊的操作の注釈を付ける)。宣言から作ったJSON Schemaで検証 |

AIの実体は2通りに対応します。外部エージェント(Claude Codeなど)をMCPで繋ぐ形と、アプリ内のチャットパネルからAPIを直接呼ぶ形です。チャットパネルはAnthropic APIとOpenAI互換エンドポイントを切り替えられるようにし、内部では上のMCPツールを同じように使います。パネルからの依頼には現在のスケッチ、選択中のタイムライン区間、プレビュー画像を自動で添付します。

AIの変更はすべて自動で履歴(git)に残し(MCP経由はツール呼び出しごと、ファイルの直接編集は変更が5秒止まった時点で1コミット)、サムネイル付きで履歴に並べます。「3つ前の方がよかった」をクリック1回で戻せ、「この案を元に3パターン」と頼むと枝分かれした案を並べて比較できます。巻き戻しは対象の作品フォルダだけに適用し(git restore --source=<コミット> -- works/<作品>)、他の作品には影響させません。枝分かれした案は作品フォルダの複製として作ります。.cache/ と renders/ はgitに入れず、100MBを超える素材も対象外にして内容ハッシュをproject.jsonに記録し、コミットから元の素材を確かめられるようにします。自動コミットの前にgitのロックを確認し、Claude Codeなど外部のgit操作と重なったら待って再試行します。

**エージェント用スキル**: Remotionは2026年1月にAIエージェント向けのルールファイル(Agent Skills)を公開し、HyperFramesも制作手順を教えるスキルを同梱しています。このアプリも同じ形で、スケッチの書き方、音・MIDIへの反応のさせ方、合成、書き出しまでの手順をSKILL.md群として同梱し、Claude Codeなどが必要なときだけ読み込めるようにします。テンプレートは「音に反応するパーティクル」「歌詞タイポグラフィ」「MIDIドラム可視化」など実際に動く最小例として用意し、AIがそこから派生させます。

**編集の検証**: project.jsonとイベント対応表にはJSON Schemaを用意し、AIの編集結果を読み込み前に検証します。不正な値は読み込まず、理由を `get_diagnostics` で返します。変更の直後には該当区間のコンタクトシートを自動で作り、AIが見た目を確認してから完了を報告する手順をスキルに書いておきます。render\_framesとrender\_contact\_sheetが返す画像は既定で長辺1024pxのJPEGにし、原寸が要るときはファイルパスで返します。

**同時編集の整合**: project.jsonを書き換えるのはRustコアだけです。UIとMCPツールは「この値をこう変える」という操作をRustコアに送り、Rustコアが改訂番号(最後に読んだ内容の版)を確かめて適用します。AIや外部エディタがファイルを直接書いた場合はファイル監視で検知し、差分を1つの操作として取り込みます(自分が書いた内容はハッシュで見分けて無視)。取り消し履歴はRustコアが操作単位で持ち、MCP経由のAIの1回の変更は1つの取り消し単位かつgitの1コミットになります。履歴(git)の区切りは、MCP経由の変更はツール呼び出し単位、AIや外部エディタによる直接編集とUIでの人の操作は「変更が5秒止まった時点」で1コミットにします(直接編集ではAIと人を区別できないため、作者は「外部編集」とする)。自動保存は作業ツリーに書くだけでコミットしません。書き出し開始時は必ずコミットし、書き出しファイル名のコミットIDが内容と一致するようにします。外部から不正なproject.jsonが書かれた場合は、修正されるまでRustコアの書き込みを止め(UIの編集は保留にする)、内容を上書きしません。外部の書き込みとUIの操作が重なった場合は、最後に読んだ版を基準にJSONパス単位で差分を合成し、同じパスが衝突したときは外部側を優先して、捨てたUIの操作を診断と取り消し履歴に残します。

**接続方式**: 外部エージェントにはCLIの `sb mcp` をstdioのMCPサーバーとして登録します。`sb mcp` はstdioと、Rustコアが名前付きパイプで公開するMCPサーバーの間を中継し(rmcpの `transport-async-rw` は読み書きできる任意の非同期ストリームを接続に使えるため、tokioの `NamedPipeServer` / `NamedPipeClient` をそのまま渡す)、アプリが未起動なら非表示で起動します。アプリは単一インスタンスで動き、CLIの `sb render` も同じインスタンスに依頼します。中継の認証トークンはユーザー設定フォルダに保存し、エージェント側の設定は固定のままで済むようにします。

## UI(Blender式)

画面構成と操作はBlenderの方式に揃えます。

**エリアとエディタ**: 画面は「エリア」の分割で構成し、各エリアは左上のメニューで表示するエディタの種類を切り替えます。エリアの角をドラッグすると分割、隣のエリアへドラッグすると結合し、`Ctrl+Space` でカーソル下のエリアを最大化・復帰します。どのエディタもどのエリアにも置け、同じエディタを複数開くこともできます。

| エディタ | 機能 |
| --- | --- |
| プレビュー | 解像度倍率切替、セーフエリア表示、fps・フレーム時間表示。エラー時は直前の正常なコードで描画を続け、エラーを重ねて表示 |
| コード | CodeMirror 6。TypeScript 7の言語サーバーによる型補完、保存でホットリロード、AIが書き換えた箇所の差分表示 |
| タイムライン | 波形、ピアノロール、マーカー、ループ範囲、BPMグリッドへの吸着、クリップトラック |
| グラフエディタ | キーフレームのカーブとイージングの編集 |
| パラメータ | params宣言から自動生成したスライダー・色・トグル、MIDI CCの割り当て |
| アセット | ドラッグ＆ドロップでassetsへコピーし、解析を開始。イベントMIDIの対応表もここで編集 |
| チャット | アイデアを文章で渡す。プレビュー上を囲んで「ここを」と指示できる |
| 履歴 | 履歴(コミット)のサムネイル一覧、2案の並列プレビュー |
| コンソール | ログ、例外、フレーム時間の推移 |
| 書き出し | 出力設定とレンダーキュー |

**ワークスペース**: 上部のタブでエリア配置を丸ごと切り替えます。配置の変更はワークスペースごとに保持され、追加・複製・名前変更ができます。配置は作品ごとに保存し、「初期設定として保存」で新規作品の既定にもできます(Blenderのスタートアップファイル相当)。

| 初期ワークスペース | 構成 |
| --- | --- |
| アイデア | チャット、プレビュー、履歴 |
| コード | コード、プレビュー、コンソール、パラメータ |
| タイミング | プレビュー、タイムライン、グラフエディタ、パラメータ |
| 素材 | アセット、プレビュー、タイムライン |
| 書き出し | プレビュー、書き出し |

**操作の挙動**:

- ショートカットはカーソル下のエリアに対して働き、同じキーでもエディタごとに意味が変わる
- `F3` で全操作を名前検索して実行する
- 数値フィールドは左右ドラッグで増減、`Ctrl` で刻み、`Shift` で微調整、ダブルクリックで数値入力。縦に並んだ複数のフィールドを上下になぞって一括編集できる
- パラメータにカーソルを乗せて `I` でキーフレームを打ち、`Alt+I` で削除する
- ツールチップにその項目をコードから参照する式(`p.density` など)を表示し、右クリックでコピーできる。AIへの指示にそのまま貼れる
- `N` でサイドバー、`T` でツールバーを開閉する
- 全操作を取り消し履歴に積む(`Ctrl+Z` / `Ctrl+Shift+Z`)
- キー割り当てはBlenderの初期値に合わせ、設定で変更できる。コードエディタやチャットで文字を入力中は、その入力欄のキー操作を優先する

起動時は作品一覧(サムネイルは最新の履歴)と「新規」入力欄を表示します。入力欄にアイデアを書いて音声やMIDIを落とすと、フォルダ作成から最初の実装までAIが行い、「アイデア」ワークスペースで開きます。

**実装**: エリア管理はBlender風レイアウトのWeb Componentであるsliced-areasを土台にします。まだ初期段階のライブラリなので、フォークして自分で保守する前提にします。レイアウトは各エリアの矩形を0〜1の座標で持つ単純なデータなので、足りない機能があれば自作に切り替えても影響は小さく済みます。sliced-areasから使うのはレイアウトのデータ形式とイベント(layoutchange、cornerclick)が中心で、分割・結合・最大化の操作は足りない分を自作する前提で見積もります。パラメータエディタはTweakpane v4にキーフレーム用のボタンを足して作ります。各エディタには「外部エディタで開く」を置き、VS Codeなどで編集しても保存で反映されます。

## 技術スタック

描画はブラウザ技術(WebGL2/WebGPU/Canvas)で行い、重い処理とファイル入出力はRustコアに任せます。AIが最も正確に書けるのがJS/TSとGLSLであること、バンドル不要でホットリロードできることが理由です。

| 層 | 採用候補 |
| --- | --- |
| アプリ基盤 | Tauri 2(Rust)+ WebView2、フロントはVite + TypeScript。Rustは app/rust-toolchain.toml で 1.97.0 に固定する(Oxc 0.158 が Rust 1.97 を要求する。0.133 は宣言上 1.93 対応だが実際にはビルドできなかった) |
| UI | Solid、sliced-areas、Tweakpane v4、CodeMirror 6 |
| 描画 | Canvas2D、WebGL2(twgl.js)、three.js、p5.js 2.x(互換アドオン付き)、Hydra、ISFシェーダー、HTML、WebGPUは後日 |
| 時間制御 | timeweb方式の仮想時計(自前) |
| ビルド | Oxc(TS変換)、oxc\_resolverとimport map(依存の解決)、pnpm(取得)、TypeScript 7(型チェックと言語サーバー) |
| 動画入出力 | WebCodecs + Mediabunny(圧縮形式)、ffmpegをサイドカーとして同梱(ProRes・GIF・WebM、音声の多重化と色情報の書き込み、H.264の代替経路、動画プロキシ)、EXRはRustのexrクレートで書き出す |
| 音声解析 | Symphonia(デコード)、rustfft、beat-thisクレート(Beat This!のRust移植。rtenでONNXを実行) |
| MIDI・ボーカル合成 | midir(ライブ入出力)、midly(.midの読み込み)、utaformatix-ts(svp・vsqx・ustxなど)、.rppのマーカー抽出 |
| ファイル監視 | notify(Rust) |
| AI接続 | rmcp(MCP公式Rust SDK)、チャットパネルはAnthropic APIとOpenAI互換エンドポイントに対応 |
| 履歴 | git(MinGitを同梱して実行。gitoxideは履歴一覧と差分の読み取りに使う) |
| ライブ出力(後段) | spout-rs、grafton-ndi |
| AEプラグイン(任意) | after-effectsクレート(Rust) |

CLI(`sb render`)はRustの実行ファイルとして作り、同じアプリを非表示ウィンドウで起動して描画させることで、描画エンジンを一つに保ちます。

## AEプラグイン(任意)

同じスケッチをAE上でプリレンダなしに動かすことは可能で、プリレンダでの運用とも競合しません。AEのエフェクトプラグインは薄い中継役にし、描画は起動中のこのアプリが行います。

1. AEが時刻tのフレームを要求する
2. プラグインが作品名とレイヤーID、t(作品時刻)、解像度、パラメータ値、入力レイヤーのピクセルをローカル通信(共有メモリまたはソケット)でアプリへ送る
3. アプリがオフスクリーンで描画し、ピクセルを返す
4. プラグインがAEの出力バッファへ書き込む

描画を時刻tの関数にしていることがここで効きます。AEはフレームを順不同かつ並列に要求するので、前フレームに依存するコードは動きません。`simulate` を使うスケッチは保存点からの再計算になるため、初回の描画が遅くなります。

| 項目 | 方針 |
| --- | --- |
| パラメータ | AEのエフェクトパラメータは事前に固定数で宣言するため、汎用スライダーと色を一定数用意し、スケッチのparamsに順に割り当てる。AEのキーフレームで動かせる |
| 入力レイヤー | エフェクトを適用したレイヤーをテクスチャとしてスケッチに渡し、素材を加工するエフェクトとしても使えるようにする |
| 音声・MIDI | アプリ側の解析結果を使う。AEのコンポジション時刻と作品時刻のオフセットだけ指定する(レイヤー時刻への変換はアプリ側で行う) |
| 制約 | アプリを起動しておく必要がある。フレームごとに通信が発生するため、AE上のプレビューはアプリ単体より遅い。Windows版のみビルドする |
| クリップトラック | アプリ側のproject.jsonの値を使い、AEのパラメータには割り当てない(AE上では編集できない)。時刻は音声・MIDIと同じオフセットで対応させる。ISF4AE単体で読み込む場合はtracksを使えない |

AEプラグインで扱うのは純粋・状態ありスケッチに限り(逐次スケッチは不可)、フェーズ1からオフスクリーン描画を前提にしておけば、プラグインは後から足せます。

**実装の参考**: AEプラグインはRustの[after-effects](https://github.com/virtualritz/after-effects)クレートで書けます。Gyroflowのように純RustでGPU描画するプラグインの実例があり、通信部分のコードをRustコアと共有できます。シェーダーだけで書いたスケッチはISF形式なので、[ISF4AE](https://github.com/baku89/ISF4AE)(MIT)など既存のAEプラグインでアプリなしに読み込めます。その場合は通信が不要で、AE上でも速く動きます(ISF4AEは永続バッファなど一部の機能に未対応)。

## 開発フェーズ

フェーズ1で「Claude Codeにアイデアを渡す→プレビュー→MP4(音声なし)」が成立し、フェーズ3でAIが描画結果を自分で確かめながら直せるようになり、フェーズ4で長尺の本番制作に使える状態になります。

0. **技術検証**: 「先に検証する技術リスク」の9点を試作で確かめ、代替案の要否を決める(完了条件: 9点すべての採否と計測値を表に記録した)
1. **最小ループ**: Tauriアプリの骨格(Rustコア、UI WebView、スケッチWebView)、仮想時計付きランタイム(Canvas2D・WebGL・ISFシェーダー・p5)、Oxcによるビルドとホットリロード、シークバーだけのタイムライン、WebCodecsでのMP4と連番PNG書き出し、`AGENTS.md`・型定義・最初のスキル。git導入(フェーズ3)までは、書き出しファイル名にコミットIDの代わりに内容ハッシュを入れる(完了条件: Claude Codeが書いたp5スケッチをプレビューし、1080p30の10秒MP4を書き出せる)
